## TypeScript 7 deviations

`E00_S01_T01` installed `typescript@7.0.2`, the **native** compiler. The task file was written
before that was known, so every mandated option was verified empirically rather than assumed. Two
deviations were forced. Neither drops a requirement, and `typescript.ignoreBuildErrors` was never
used.

### Deviation 1 — `baseUrl` has been **removed** in TypeScript 7

This is the risk the `T01` handoff flagged, and it is now a hard error, not a deprecation warning.
The task file's exact config fails outright:

```
$ npm run typecheck
tsconfig.json(20,5): error TS5102: Option 'baseUrl' has been removed. Please remove it from your configuration.
  Use '"paths": {"*": ["./*"]}' instead.
TYPECHECK_EXIT=1
```

**Resolution: `baseUrl` was dropped; `paths` was kept unchanged as `"@/*": ["./src/*"]`.** In
TypeScript 7 `paths` entries resolve relative to the directory containing `tsconfig.json`, which is
the repository root, so `./src/*` means exactly what `baseUrl: "."` previously made it mean. This is
precisely the fallback the `T01` handoff pre-authorised.

The alias is not merely accepted — it is proven to resolve under **both** resolvers, which are
separate implementations (`tsc` 7 and Next 16's Turbopack). `tsc` resolving it:

```
$ printf 'import { siteName } from "@/app/site-metadata";\nexport const n: string = siteName;\n' > strictness-probe.ts
$ npx tsc --noEmit ; echo "ALIAS_EXIT=$?"
ALIAS_EXIT=0
```

and Turbopack resolving it, since `layout.tsx` and `page.tsx` both import via `@/app/site-metadata`
and `next build` compiles and prerenders them successfully.

**Acceptance criterion 3 ("`tsconfig.json` sets `baseUrl: "."`") therefore cannot be met as
written.** The intent behind it — a working `@/*` → `./src/*` alias — is fully met. This is recorded
as a deviation rather than a pass, because the compiler removed the option.

### Deviation 2 — Next 16 mandates `jsx: "react-jsx"`, not `"preserve"`

The task specifies `"jsx": "preserve"`. Next 16 overwrites it on the first build:

```
  We detected TypeScript in your project and reconfigured your tsconfig.json file for you.
  The following mandatory changes were made to your tsconfig.json:

  	- jsx was set to react-jsx (next.js uses the React automatic runtime)

  The following suggested values were added to your tsconfig.json:

  	- include was updated to add '.next/dev/types/**/*.ts'
```

Next calls this a **mandatory** change and rewrites the file itself. Forcing `"preserve"` back would
make every single build dirty the working tree, breaking the story's "`git status` is clean
immediately after a build" criterion. The rewritten values were therefore accepted as the fixed
point, and `.next/dev/types/**/*.ts` was kept alongside the original `.next/types/**/*.ts`.

No acceptance criterion names `jsx`, so nothing fails here — but the file no longer matches the
literal block in the task description, so it is recorded.

**The formatting is mine, not Next's.** Next expanded every array onto separate lines when it
rewrote the file. Re-writing it in the compact form and rebuilding proved Next only rewrites when a
*value* needs changing, and leaves formatting alone otherwise:

```
$ npm run build > /tmp/build3.log 2>&1 ; echo "BUILD3_EXIT=$?"
BUILD3_EXIT=0
$ diff /tmp/tsconfig.compact.json tsconfig.json && echo "TSCONFIG_FORMATTING_PRESERVED"
TSCONFIG_FORMATTING_PRESERVED
```

This matters for `E00_S02`: Prettier can format `tsconfig.json` without fighting Next.

### 2. `next-env.d.ts` content differs between `next dev` and `next build`

A genuine trap for `E00_S03`/`E00_S04`. The generated file points at different type directories
depending on which command last ran:

```
$ diff <build-version> <dev-version>
3,4c3,4
< import "./.next/types/routes.d.ts";
< import "./.next/types/root-params.d.ts";
---
> import "./.next/dev/types/routes.d.ts";
> import "./.next/dev/types/root-params.d.ts";
```

**The committed version is the `next build` variant**, because that is what CI produces and what
keeps `git status` clean after a build. A developer who runs `npm run dev` will see `next-env.d.ts`
show as modified; that is expected noise and must not be committed over the build variant. If CI
ever adds a "no uncommitted changes after build" gate, it must run `build`, not `dev`, before it.

Confirmed the committed variant is stable across repeated builds (`NEXTENV_STABLE_AFTER_BUILD`), and
that `npm run typecheck` still exits 0 on a tree with **no** `.next/` at all — simulating a fresh
clone — because `skipLibCheck` covers the unresolvable references:

```
$ mv .next /tmp/next-backup && rm -f tsconfig.tsbuildinfo
$ npm run typecheck ; echo "FRESH_TYPECHECK_EXIT=$?"
FRESH_TYPECHECK_EXIT=0
$ npm run build ; echo "FRESH_BUILD_EXIT=$?"
FRESH_BUILD_EXIT=0
```

So `npm ci && npm run typecheck` works on a fresh clone before anything has been built.
