# Task: ESLint flat config with type-aware rules and lint scripts

## Description

Stand up ESLint as the project's correctness linter, in flat-config form, with **type-aware**
typescript-eslint rules enabled, and add the `lint` and `lint:fix` scripts.

Assumes `E00_S01` has landed: `tsconfig.json` exists in strict mode with the `@/*` → `./src/*`
path alias, and there is a `src/` tree containing `src/app/layout.tsx` and `src/app/page.tsx`.

This task does **not** configure Prettier — `E00_S02_T01` owns that and runs in parallel. What this
task owns is the boundary between the two tools, expressed as one line of config plus a comment.

### The division of responsibility — already decided, not up for rediscovery

**Prettier owns formatting exclusively. ESLint never reports a formatting rule.** The two tools
overlap by default and the overlap produces contradictory autofixes: one tool's fix is the other
tool's violation, and the developer is left running them alternately forever.

`eslint-config-prettier` is therefore the **last** element of the exported flat-config array, so it
switches off every stylistic rule the earlier layers turned on. If a diff is about whitespace,
quotes or line width, Prettier decides. If it is about correctness, ESLint decides.

**Record this decision as a comment block at the top of `eslint.config.mjs`**, immediately above
the config array, including the reason. Do not create a page under `docs/` for it — `E00_S05` owns
the `docs/` layout and its index table, and a page added here would land outside that convention.
The config file is where the next reader looks anyway.

### Dependencies

Add as **devDependencies** with caret ranges:

- `eslint`
- `@eslint/js`
- `typescript-eslint`
- `eslint-config-next`
- `eslint-config-prettier`

Add only these and only the two scripts below. `E00_S02_T01` and `E00_S02_T03` are adding their own
dependencies and scripts in parallel; every extra line here becomes someone else's merge conflict.

### `eslint.config.mjs`

Flat config at the repository root, **the array form**. `.eslintrc*` is not used and must not be
created — two competing config formats in one repository is exactly the drift this project avoids
elsewhere.

Composition, in this order:

1. `@eslint/js` recommended.
2. `typescript-eslint` **type-aware** recommended (`tseslint.configs.recommendedTypeChecked`).
3. `eslint-config-next`.
4. `eslint-config-prettier` — **last**.

### Enabling type-aware linting

Type information is what makes rules such as `@typescript-eslint/no-floating-promises` and
`@typescript-eslint/no-misused-promises` possible at all. Point typescript-eslint at the project:

```js
languageOptions: {
  parserOptions: {
    projectService: true,
    tsconfigRootDir: import.meta.dirname,
  },
},
```

This is measurably slower than syntactic linting. It is worth it, and that trade-off is recorded in
the same comment block as the Prettier decision.

Type-aware rules must not be applied to non-TypeScript files (`eslint.config.mjs` itself,
`next.config.ts` handling aside). Use `tseslint.configs.disableTypeChecked` scoped to `**/*.{js,mjs,cjs}`
so linting the config file does not fail for want of a tsconfig entry.

**Do not modify `tsconfig.json`.** `E00_S01`'s DoD requires that this story adds tooling without
changing the strictness settings or the path alias. If type-aware linting appears to require a
tsconfig change, stop and raise it as a story amendment rather than editing the file.

### Ignores

`eslint.config.mjs` declares its ignores through a `{ ignores: [...] }` entry mirroring
`.gitignore` plus the board:

- `node_modules/`
- `.next/`
- `out/`
- `next-env.d.ts` (generated by Next, not authored)
- `project/` — the scrum board is Markdown, not source

`src/` and `scripts/` are **not** ignored and must never be. (`scripts/` does not exist yet;
`E00_S03` creates it and expects lint to reach it.) Each ignore entry carries an inline comment
stating why it is there — an unexplained ignore is how a directory quietly stops being checked.

### Scripts

Add to `package.json`:

```json
"lint": "eslint . --max-warnings=0",
"lint:fix": "eslint . --fix"
```

`--max-warnings=0` is deliberate: **warnings fail.** A warning that never fails the build is a
comment with extra steps, and a repository that tolerates fifty of them cannot see the fifty-first.

### Proving type-aware rules are actually live

A type-aware config that silently falls back to syntactic linting looks identical from the outside
until the day it matters. Prove it, then revert:

1. Add a temporary file under `src/lib/` containing a floating promise — an `async` function whose
   returned promise is neither awaited, returned, nor `void`-ed.
2. Run `npm run lint`; it must exit non-zero and name `@typescript-eslint/no-floating-promises`
   together with the file path.
3. Delete the temporary file; `npm run lint` exits zero again.

Record the observed output of step 2 in the task's rapport. That output *is* the evidence — the
rule name only appears if type information reached the linter.

### Domain constraint

E00 is pure infrastructure. Nothing this task creates — including the temporary violation file used
in the proof — may reference a kommun, skola, nyckeltal or data source.

## Acceptance Criteria

- [ ] `eslint.config.mjs` exists at the repository root in flat-config array form, and no
      `.eslintrc`, `.eslintrc.js`, `.eslintrc.json` or `.eslintrc.cjs` exists anywhere in the
      repository.
- [ ] The config composes, in order: `@eslint/js` recommended, `typescript-eslint`
      type-aware recommended, `eslint-config-next`, and `eslint-config-prettier` **last**.
- [ ] `eslint`, `@eslint/js`, `typescript-eslint`, `eslint-config-next` and `eslint-config-prettier`
      are in `devDependencies` with caret ranges, and `package-lock.json` is updated and committed.
- [ ] `parserOptions.projectService` (or an equivalent explicit `project` setting) is configured so
      typescript-eslint has type information, and `tsconfig.json` is unchanged by this task
      (`git diff` against the pre-task tree shows no modification to it).
- [ ] A comment block at the top of `eslint.config.mjs` records the Prettier-owns-formatting
      decision, the reason for it, and the reason type-aware linting is accepted despite being
      slower.
- [ ] The `ignores` entry covers `node_modules/`, `.next/`, `out/`, `next-env.d.ts` and `project/`,
      each with an inline comment stating why, and covers neither `src/` nor `scripts/`.
- [ ] `package.json` contains exactly the scripts `lint` (`eslint . --max-warnings=0`) and
      `lint:fix` (`eslint . --fix`), in addition to the scripts already present from `E00_S01`.
- [ ] `npm run lint` exits zero on the clean tree.
- [ ] A temporary file containing a floating promise causes `npm run lint` to exit non-zero, naming
      both the file path and `@typescript-eslint/no-floating-promises`; the recorded output is
      captured in the rapport.
- [ ] That temporary file is removed and `npm run lint` exits zero again, with `git status` clean.
- [ ] A deliberate non-type-aware violation (for example an unused variable) also makes
      `npm run lint` exit non-zero and names the file and rule; it is then removed and lint passes.
- [ ] Linting `eslint.config.mjs` itself does not error for want of a tsconfig project entry.
- [ ] No file created or modified by this task references a kommun, skola, nyckeltal or data source.
